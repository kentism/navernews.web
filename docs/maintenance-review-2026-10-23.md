## 1. 운영에서 확인한 백업 인증 오류와 비어 있는 학습 데이터

우선순위: 높음. 현재 확인된 운영 문제.

운영 API 응답:

| 항목 | 확인 결과 |
| --- | --- |
| `/healthz` | HTTP 200, `status: ok` |
| 서버 DB | 존재, 쓰기 가능, 53,248 bytes |
| 최종 클리핑 문서 | 0건 |
| 최종본 학습 이벤트 | 0건 |
| 전체 클리핑 이벤트 | 5건 |
| 기사 / 후보 / 후보 검색어 | 각각 0건 |
| 백업 설정 | GitHub, 설정값 및 토큰 존재 |
| 실제 GitHub 백업 조회 | `GitHub backup download failed with status 401.` |
| 복원 가능 표시 | `false` |

`configured: true`는 환경변수 존재 여부만 판단한다. 토큰이 유효하거나 백업 데이터가 존재한다는 뜻은 아니다. `restore_available: false` 역시 현재는 GitHub 파일을 읽지 못한 결과라서 백업이 없다는 증거가 아니다.

401은 유효하지 않은 인증정보와 부합한다. 만료, 폐기 또는 잘못 설정된 토큰 등이 가능하지만 정확한 원인은 GitHub/Koyeb 설정을 확인해야 한다. 별도 GitHub 연결로도 저장소와 파일이 404로 반환되어 접근하지 못했다. 비공개 저장소 권한 문제와 실제 파일 부재를 구분할 수 없으므로 과거 학습 데이터의 소실 여부는 미확인이다.

조치 순서:

1. 로그인 상태에서 `/api/storage/export`로 현재 서버 데이터를 먼저 별도 보관한다.
2. GitHub의 `kentism/navernews-backup` 저장소에서 `main` 브랜치의 `navernews/clipping_backup.json` 및 커밋 이력을 확인한다. 마지막 유효한 백업의 학습 건수와 시각을 확인한다.
3. 필요한 경우 GitHub 토큰을 갱신한다. 대상 저장소는 `kentism/navernews-backup`, 저장소 권한은 `Contents: Read and write`로 지정한다.
4. **사용자가 직접 입력할 값:** Koyeb의 해당 서비스 → Settings → Environment variables → `BACKUP_GITHUB_TOKEN`에 새 토큰을 설정한다. 토큰을 소스나 문서에 넣지 않는다. 다른 백업 변수는 기존 응답상 설정되어 있다.
5. 환경변수 적용 시 서비스가 다시 시작될 수 있으므로, 위 데이터 보관과 백업 확인을 먼저 마친다. 현재 코드는 학습 데이터가 비어 있으면 시작할 때 GitHub 자동 복원을 시도한다.
6. 적용 후 `/api/storage/learning-status`에서 `backup_learning.available`, 서버와 백업의 학습 건수 및 마지막 학습 시각을 다시 대조한다.

기존 유효한 백업을 확인하기 전에 빈 서버 데이터를 수동 백업으로 업로드하지 않는다. 백업 파일의 현재 버전을 덮어쓸 수 있다.

근거: `services/storage_backup.py:32`, `routers/storage.py:101` 및 운영 API 응답.

## 2. 저장과 백업 실패를 구분하지 못하는 경로

우선순위: 높음. 로컬 모의 장애로 재현.

- 최종본 생성은 문서를 먼저 커밋하고 기사별 이벤트를 각각 저장한다. 이벤트 저장 중 예외가 나면 문서만 남을 수 있다.
- 중간 저장 실패를 주입한 결과 문서 1건, 학습 이벤트 0건이 남았다. 같은 내용을 다시 제출하면 `duplicate: true`로 반환하여 빠진 이벤트를 복구하지 않았다.
- 자동 백업 처리와 시작 시 복원 처리에서 `httpx.ReadTimeout`, `httpx.ConnectError`를 잡지 않는다. 실제로 해당 예외를 주입하면 처리 함수 밖으로 전파됐다.
- 따라서 DB 저장 이후 백업 통신 시간 초과가 발생하면 화면에 전체 저장 실패로 표시될 수 있다. 빈 DB로 시작할 때 복원 통신 오류가 나면 앱 시작 자체가 실패할 수 있다.
- 중복 최종본 제출은 백업을 생략한다. 모의 확인에서 중복 재시도 시 업로드 호출은 0회였다. 앞선 백업 실패를 같은 버튼으로 재시도할 수 없다.

보완 방향:

- 최종본 문서와 기사별 학습 이벤트를 하나의 SQLite 트랜잭션으로 저장한다.
- 서버 저장 성공과 원격 백업 성공을 별도 상태로 반환하고 화면에 표시한다.
- 백업 통신 예외를 처리하고 재시도 가능 상태를 기록한다. 시작 시 복원 실패도 앱 시작 여부와 분리하되, 데이터 미복원 상태를 명확하게 노출한다.
- 마지막 백업 성공 시각, 실패 사유, 아직 백업되지 않은 변경 유무를 지속적으로 표시한다.
- 중복 제출에서도 이전 백업 실패를 재시도하거나 별도의 백업 재시도 버튼을 제공한다.

근거: `services/clipping_store.py:1451`, `routers/clippings.py:38`, `routers/clippings.py:77`, `services/storage_orchestrator.py:98`, `main.py:169`.

## 3. 일부 API 인증 누락과 기사 텍스트의 HTML 처리

우선순위: 높음. 소스 확인 및 로컬 모의 검증. 운영 서버에 공격성 요청은 보내지 않았다.

- `/api/article`은 로그인 검증 없이 전달받은 URL을 서버에서 조회한다. URL에 대한 내부망 차단도 없고 리디렉션을 따라간다. 외부에서 서버에 임의 주소 조회를 시킬 수 있어 접근 제한이 필요하다.
- `/api/stream/notifications`도 로그인 검증 없이 연결을 허용한다.
- 검색 강조 함수는 입력을 HTML 문자로 이스케이프하기 전에 `Markup`으로 신뢰한다. `<img ...>` 형태의 모의 문자열이 그대로 남는 것을 확인했다. 외부 제목/요약에 HTML처럼 해석되는 문자가 포함되면 화면에 HTML로 삽입될 여지가 있다.

보완 방향:

- 기사 조회와 알림 연결에 공통 인증을 적용한다.
- 기사 조회는 허용한 HTTP(S) 목적지만 처리하고, 내부 IP 및 리디렉션 이후 목적지를 검증한다. 현재 화면에서 쓰지 않는 엔드포인트라면 제거 여부도 검토한다.
- 제목/요약을 먼저 이스케이프한 뒤 서비스가 만든 강조 태그만 허용한다.

학습 이력의 별도 비밀번호는 기존 요구대로 브라우저 잠금으로 구현되어 있다. 서버 API의 관리자 권한 검증을 대신하는 구조는 아니므로, 여러 사람에게 로그인 권한을 공유할 경우에는 추가 설계가 필요하다.

근거: `routers/search.py:62`, `services/news_service.py:124`, `routers/notifications.py:28`, `main.py:69`, `static/js/clipping_service.js:9`.

## 4. 후보 수집 기간과 학습 범위의 실제 동작

우선순위: 중간. 코드에서 확인한 기능상 제약.

### 한국 시간 기준의 오늘 00시

`오늘 00시부터`가 UTC 자정으로 계산된다. 한국 시간 2026-10-23 08:30을 대입하면 기준 시각은 2026-10-22 09:00으로 계산됐다. 한국 자정과 일치하지 않으며, 오전 작업 시간대에 전날 기사가 더 포함될 수 있다. `Asia/Seoul` 자정을 구한 뒤 UTC로 변환하도록 수정하는 것이 적절하다.

근거: `routers/candidates.py:128`.

### 학습 이력 저장량과 실제 점수 계산에 쓰는 범위

이력 자체는 누적되지만, 일반 후보 점수 계산에서는 최근 최종본 학습 기사 80건과 제외 기사 80건만 읽는다. 전체 누적 이력이 모두 매번 판단에 사용되는 구조가 아니다. 출처 가산점도 최근 사례에 한 번 포함되면 적용되므로 엄밀한 빈도 학습과는 차이가 있다.

장기 사용 의도에 맞게 전체 이력의 출처/주제 통계를 누적하고, 최근 사례와 장기 통계를 어떤 비율로 반영할지 정해야 한다. 현재 동작을 유지한다면 UI에도 실제 반영 범위를 명시하는 편이 좋다.

근거: `services/clipping_store.py:614`, `services/clipping_store.py:646`.

### 많은 검색 결과에서의 수집 누락 표시

후보 수집은 검색어당 최대 5페이지 × 100건을 조회한다. 기사량이 많으면 기간의 시작점에 닿기 전에 수집이 끝나지만, 응답에는 조회 한도 도달 여부가 없다. 외부 검색 실패도 빈 결과로 바뀌어 완료처럼 보일 수 있다. `기간 전체 수집 완료`, `조회 한도 도달`, `외부 API 실패`를 구분하는 것이 필요하다.

근거: `routers/candidates.py:159`, `services/news_service.py:80`.

## 5. 백업 파일이 커졌을 때의 복원 한계

우선순위: 중간. 장기 누적 시 문제이며 현재 원격 백업 크기는 미확인.

현재 다운로드는 GitHub Contents API의 Base64 `content`만 읽는다. GitHub는 1MB 초과 파일에 다른 응답 방식을 요구하고, `object` 응답에서는 `content`가 빈 문자열이 될 수 있다. 이 응답을 모의 주입하면 `JSONDecodeError`로 실패했다.

GitHub 공식 문서: <https://docs.github.com/en/rest/repos/contents#get-repository-content>

`raw` 응답을 지원하거나 Git Blob API를 사용하는 방식으로 큰 파일도 읽도록 보완하고, 백업 크기를 상태 화면에 표시해야 한다. 최종본/학습 이력을 보존하면서 임시 데이터와 불필요한 중복 데이터만 정리하는 보존 정책도 검토할 수 있다.

근거: `services/storage_backup.py:114`.

## 6. 다음 배포의 재현성과 자동 점검

우선순위: 중간.

- `requirements.txt`의 패키지 버전이 고정되어 있지 않다. 같은 소스라도 새 이미지 빌드 시 다른 버전 조합이 설치될 수 있다.
- Docker의 `python:3.12-slim`도 변경 가능한 태그다. 검증한 기본 이미지와 의존성 조합을 기록하고 정기적으로 갱신하는 방식이 적절하다.
- GitHub Actions는 현재 이미지 빌드/푸시를 수행하지만 기존 테스트와 JS 문법 검사를 실행하지 않는다.
- 월 1회 정도 의존성/보안 업데이트를 검토하고, 테스트 통과 후 고정 버전을 갱신한다. 업데이트마다 버전을 무조건 최신으로 올리는 작업은 권하지 않는다.
- 운영 반영 이미지는 가능하면 커밋 SHA 태그로 추적하고, 직전 정상 이미지로 되돌릴 경로를 유지한다.

pip 공식 문서: <https://pip.pypa.io/en/stable/topics/repeatable-installs/>

근거: `requirements.txt:1`, `Dockerfile:1`, `.github/workflows/docker-image.yml:22`.

## 검증 결과와 미확인 범위

- Python 기존 테스트: 30개 통과. 로컬 Python 3.14.2 환경에서 실행했으며, 운영 Docker의 Python 3.12 환경과는 다르다.
- 복사 형식 JS 테스트: 5개 통과.
- JS 3개 파일: `node --check` 통과.
- 추가 모의 검증: 백업 통신 예외 전파, 저장 도중 중단과 중복 재시도, 인증 없이 기사 조회 함수 진입, 제목의 HTML 미이스케이프, 큰 백업 응답 처리 실패, 한국 자정 계산 오류를 확인했다.
- Windows 샌드박스에서는 asyncio 내부 로컬 소켓 생성이 멈췄다. 샌드박스 밖에서 외부 통신을 mock으로 차단하고 기존 테스트를 다시 실행하여 통과했다. 이 현상은 운영 장애로 판단하지 않는다.
- 기존 테스트에는 위 백업 통신 장애, 시작 시 복원 실패, 최종본 저장의 원자성, API 인증을 검증하는 테스트가 없다. 보완 시 우선 추가할 대상이다.
- 운영 백업 저장소 내부, 과거 데이터 소실 여부, 토큰의 정확한 무효화 사유, 운영 이미지의 패키지 취약점은 미확인이다.

## 권고 작업 순서

1. 현재 서버 데이터와 기존 원격 백업을 확보하고 GitHub 인증을 복구한다.
2. 최종본 저장을 하나의 트랜잭션으로 묶고 백업 오류/재시도 상태를 분리한다.
3. 인증 누락 API와 기사 텍스트의 HTML 처리를 보완한다.
4. 한국 시간 수집 범위, 장기 학습 범위, 수집 한도 표시를 정비한다.
5. 큰 백업 파일 지원, 의존성 버전 고정, 빌드 전 자동 테스트를 추가한다.
