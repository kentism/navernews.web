# 기사 제목 확인 프로토타입

## 범위

로컬 명령행 실험 도구다. 이후 사용자 승인에 따라 추출/조회 공통 로직을 `services/article_titles.py`로 분리하고 [뉴스 카드의 수동 제목 확인](article-title-confirmation.md)에 연결했다. 이 실행 도구 자체에는 공개 URL 조회 API, 화면 버튼, 서버 백그라운드 작업, 자동 제목 교체가 없다. 학습/점수/후보 선별 기능과 무관하다. `prototypes/`는 Docker 이미지에서도 제외한다.

기존 Python 3.12, HTTPX, BeautifulSoup만 사용하며 새 의존성이나 환경변수를 요구하지 않는다. 기본 검색 표본을 얻을 때만 기존 `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET`을 사용한다. 인증정보를 보고서에 저장하지 않는다.

## 실행

저장소 루트에서 명시적으로 `--live`를 붙였을 때만 외부 요청을 수행한다.

```powershell
python -m prototypes.article_title_probe --live
python -m prototypes.article_title_probe --live --suspected-only --keyword "방송미디어통신위원회"
```

- 네이버 검색 첫 30건을 받아 허용된 URL 중 최대 6건을 선정한다. 원문 URL을 우선하고, 허용 목록에 없으면 허용된 네이버 기사 URL을 사용한다. 전체 30건 중 제외된 기사를 성공으로 계산하지 않는다.
- `--suspected-only`는 API 제목 끝이 말줄임표인 기사만 대상으로 한다. 말줄임표는 의심 조건일 뿐 잘림을 확정하는 기준이 아니다.
- 매체 다양성을 우선하되 남은 자리는 같은 호스트의 다른 기사로 채운다. 이는 무작위 표본이나 매체별 성공률 추정치가 아니다.
- 직접 지정한 공개 기사 표본은 `--samples .maintenance/title-probe/samples.json`으로 전달할 수 있다. 배열 안에는 `url`, `api_title`, 선택적인 `kind`를 둔다. 인위적으로 자른 제목은 반드시 `kind: "synthetic"`로 표시하고 실제 API 잘림 사례와 구분한다. 이 모드는 네이버 API를 호출하지 않는다.

결과 JSON은 무시 경로 `.maintenance/title-probe/result-*.json`에 저장한다. 본문 HTML은 저장하지 않으며, 결과 파일에는 공개 기사 URL/API 제목/확인한 제목과 진단 수치만 포함한다. 진단용 결과도 영구 보관용 자료가 아니므로 이용 조건에 맞는 기간 안에 수동으로 정리한다.

## 추출과 안전장치

- 기사형 JSON-LD `headline`, Open Graph 제목, Twitter 제목, headline 메타데이터, 제목 요소를 읽는다. 표준 요소의 의미는 [Schema.org](https://schema.org/headline)와 [Open Graph](https://ogp.me/)를 참고한다. 자바스크립트/이미지/광고는 실행하거나 추가 조회하지 않는다.
- API 제목과 원문 제목을 별도로 보존한다. 길이가 충분한 기존 제목 접두부와 일치할 때만 `extended`로 분류한다. 단어가 같고 말줄임표/닫는 따옴표만 다른 경우는 `punctuation_only`로 따로 표시한다. 원문에도 말줄임표가 남으면 `source_also_short`, 일치하지 않으면 `unverified`다. 서로 다른 확장 제목이 발견되면 `conflict`로 보류한다. 이 분류는 자동 교체 허가나 수동 검수 대체가 아니다.
- 정확히 지정한 HTTPS 호스트만 허용하며 인증정보 포함 URL/다른 포트/내부 IP를 거부한다. 리디렉션도 매번 재검증한다. 공개 IP를 검증한 뒤 그 IP에 연결하고 원래 호스트를 HTTP Host와 TLS SNI/인증서 검증에 사용한다. 프록시 환경변수는 사용하지 않으며 인증서 검증을 끄지 않는다. [HTTPCore SNI 문서](https://www.encode.io/httpcore/extensions/#sni_hostname)
- 동시 2건, 한 실행당 최대 6건, 기사당 DNS/리디렉션/다운로드를 포함한 전체 제한 시간 3초, 리디렉션 최대 2회, 읽은 HTML 최대 512KiB로 제한한다. DNS는 OS 비동기 리졸버를 사용하므로 OS 수준의 이름 해석이 멈추면 프로세스 종료까지는 더 걸릴 수 있다. 기사 조회는 자동 재시도하지 않는다. 네이버 API 요청 자체는 기존 검색 모듈의 제한 시간/재시도 정책을 따른다.
- 요청 수에는 리디렉션을 포함한다. `decoded_bytes`는 읽은 HTML의 압축 해제 후 크기이며 실제 회선 전송량과 같다고 보장하지 않는다. 현재는 크기가 제한된 HTML을 읽는 방식이며 HEAD 요청만으로 제목을 얻는 방식은 아니다.
- 실패와 타임아웃은 결과 상태로 남긴다. 기존 앱/클리핑 문서/초안 저장소는 어떤 경우에도 쓰지 않는다.

## 2026-10-23 소규모 실측

로컬 Windows/Python 3.12 환경에서 명시적으로 실행한 네트워크 진단이다. 자동 테스트가 아니며, 단위/통합 테스트는 외부 통신을 모의 응답으로 대체한다.

1. 혼합 표본 6건: 네이버 기사/한겨레/JTBC/뉴스1/뉴시스/연합뉴스의 6개 호스트에서 모두 제목 메타데이터를 얻었다. 원문 조회 전체 경과 시간은 약 861ms였다. 정상 제목 4건이 포함되어 복원율의 분모로 사용하지 않는다.
2. 잘림 의심 표본 6건: API 30건 중 의심 제목 9건, 허용된 URL이 있는 의심 기사 6건을 조회했다. 누락된 글자를 포함한 더 긴 제목을 5건에서 얻었고, 나머지 1건은 말줄임표와 닫는 따옴표 차이만 있었다. 이 기호 차이는 실측 후 별도 상태로 구분하도록 보완했다.
3. 두 번째 조회는 기사당 약 145~340ms, 평균 약 247ms, 동시 2건으로 전체 약 786ms였다. 별도 네이버 API 조회는 약 244ms였다. 읽은 HTML 합계는 약 1.50MiB였다. 실행 2회 전체는 API 검색 2회, 기사 조회 12회이며 중복을 제외한 기사 10건이다.

잘림 표본 6건 중 5건은 네이버 기사 페이지, 1건은 언론사 원문 페이지였다. 독립 언론사 원문 사이트 6곳에서 복원을 검증했다는 뜻이 아니다. 확인에 성공한 허용 호스트 위주의 작은 표본이며, Koyeb 서버의 성능이나 전체 언론사 복원율, 95백분위 지연 시간을 증명하지 않는다.

판단: 제한된 기사에서 제목을 추가 확보하는 기술은 실현 가능하다. 다만 전수 자동 조회나 상시 서비스 적용은 이번 실험의 결론이 아니다. 실제 도입 전에는 미지원/차단 매체, 실패 표본, 실제 배포 환경 부하와 [검색 API 이용 조건](https://developers.naver.com/notice/article/33400)을 별도로 확인해야 한다. 사용자의 명시적 요청 없이 운영 화면에 연결하거나 자동 배포하지 않는다.
